# 接口核心链路分析

把接口文档、抓包和代码归一成同一份上下文，输出按调用顺序排列、标清依赖的接口链路。

## 输入

| 来源 | 说明 | 用途 |
| :--- | :--- | :--- |
| 接口文档 | Swagger/OpenAPI、Apifox、Postman Collection、手写接口说明 | 取 method、path、入参、出参、错误码、鉴权方式 |
| 抓包 | 浏览器网络面板、HAR、代理工具导出 | 补齐文档没写的真实路径、必填项、实际错误码 |
| 代码 | 路由表、Controller、DTO、拦截器 | 补参数校验、状态机、权限注解、幂等实现 |
| 需求材料 | PRD、业务说明、状态定义 | 取业务口径：角色、规则、状态流转 |

### 取数

先取到内容再谈分析；把「文档 / 抓包 / 代码」写进链路条目的「来源依据」。

| 来源 | 取数方式 | 取不到时 |
| :--- | :--- | :--- |
| 接口文档 | 读 OpenAPI/Swagger 导出、Apifox 分享页、Collection；按接口逐条记 method + path + 入参字段与类型 + 返回结构 + 错误码 | 文档只有目录没有字段说明时，索取导出文件或让用户给几条真实响应；**不得只按接口名推断入参** |
| 抓包 | 读 HAR 或网络面板，记真实请求体、响应体、状态码、鉴权头；注意脱敏 | 抓不到时索取关键接口的请求/响应样例 |
| 代码 | 读路由注册与 Controller 方法签名，记参数校验注解、权限注解、状态机分支、幂等键 | 仓库不可访问时要求导出路由清单或接口清单 |
| 需求材料 | 解析 PRD/需求说明，取角色、状态定义、业务规则 | 只有标题时索取核心章节 |

## 执行

1. **归一化**：把每个接口登记成原子条目——`method` + `path` + 鉴权要求 + 关键入参 + 返回关键字段 + 错误码 + 副作用（写什么表、发什么消息）。多来源冲突时以抓包/代码实测为准，冲突写进「假设与待确认」。
2. **判信息是否足够**：缺「业务目标、调用者角色、状态定义」时先追问，一次不超过 3 个能改变结论的问题；缺细节用显式假设推进并记录。
3. **识别主干**：判据是「是否有角色为完成核心目标而必须调用的接口」。管理端列表、导出、字典查询默认不是主干，除非它本身就是核心目标。
4. **划分链路**：一条链路 = 一个触发条件 + 一个可独立达成的业务结果。常见三类：鉴权链（登录 → 取 token → token 校验）、业务链（查询前置数据 → 提交 → 查结果）、异步链（提交 → 轮询状态 → 回调或消息消费）。标主链路/分支链路与链路间依赖。
5. **写节点序列**：节点写「方法 + 路径 + 关键入参与返回」，并标明**数据依赖**——下游哪个入参来自上游哪个返回字段（如 `orderId ← 提交订单返回的 data.orderId`）。条件分支内联标注，不为分支单独拆链路。单链超过 20 个节点按模块拆分。
6. **标注幂等与状态**：对每个写接口标出是否幂等、幂等键是什么、成功后状态如何变化；这决定下游幂等与并发测试点。
7. **自检**：每个接口能回溯到来源；每条链路能独立成立；依赖字段上下游对得上；没有编造的 path 或字段。

## 输出格式

产物为单个 Markdown 文档，可直接另存为 `.md` 交付或入库。

- 文首写一级标题（产物名），下一行写 `> 来源：<上游产物或用户材料>｜生成：YYYY-MM-DD`
- 节标题统一用中文序号加固定名（一、xxx、二、xxx），名称不改，供下游按标题定位；模块级标题写「模块：<模块名>」
- 列表与表格用原生 Markdown，不用代码围栏包裹；代码围栏只包裹真正的代码
- 表格列序与列名、编号格式固定，不按现状重排
- 不输出 HTML、图片、Excel、CSV 或散装纯文本

## 禁止

- 不编造 path、入参字段、返回字段、错误码；缺就标 `[待确认]` 并进「假设与待确认」。
- 不靠接口名推断行为（把 `/order/list` 推成「支持筛选、排序、导出」就是这种错）。
- 不把单个接口当链路，也不把前端页面跳转当接口链路。
- 不省略鉴权方式与数据依赖：缺了这两项，下游用例无法串起来。
- 不输出测试点、用例、优先级——那是下游 Skill 的职责。
