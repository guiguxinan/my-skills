# 接口自动化脚本生成

产出能跑、失败能定位的脚本。路径与字段拿不到就占位，不猜。

## 输入

- 上游（优先）：`api-automation-feasibility-analyzer` 的「可自动化用例清单」，含用例编号、类型、改造前置。
- 单独调用：接口用例表 + 技术栈 + 接口文档（OpenAPI/Apifox/Collection）、抓包样例、测试账号。
- **定栈顺序（必须先定，再动笔）**：① 用户指定；② 目标仓库已有框架——看 `pytest.ini` / `conftest.py` / `requirements.txt` / `package.json` / `AGENT.md` / `README.md`，沿用它的目录、命名、fixture 与报告工具；③ 都没有再追问并给推荐默认。文档与代码冲突时以代码为准，差异写进「待补清单」。
- **取真实契约**：依次取——OpenAPI/Collection 导出 → 抓包的真实请求与响应样例 → 占位 `[待补:所需信息]` 且该用例标记跳过。禁止按接口名推断入参与返回。
- 硬约束：不编造 path、字段名、业务码；不写只打印不断言的伪测试。

## 执行

1. **骨架**：能沿用目标仓库就不新建；新建时按「一个业务模块一处 Client + 一处数据 + 一处用例」，三者模块名对齐。
2. **分层职责**：Client 只放请求构造、鉴权头、序列化与响应解析，不写断言与业务判断；用例层只写业务步骤与断言；前置数据、token 获取、清理放 fixture；地址、超时、重试策略集中配置。
3. **鉴权**：token 统一由 fixture 获取并复用（登录接口一次、过期重取），不在每条用例里重复登录；凭据走环境变量或本地配置，不写进代码与日志。
4. **断言**：每条用例至少一个业务级断言，且**传输层与业务层分开判**——HTTP 状态码、业务码、关键字段值与类型、副作用（落库记录、状态变更、消息发出）；响应结构用契约或 schema 校验关键字段，不做整包全等比较（会因无关字段变动误报）。失败信息要能看出期望值与实际值。
5. **依赖顺序**：上下游有数据依赖时，用 fixture 或显式步骤按顺序构造并传递（`orderId ← 上一步 data.orderId`），不依赖用例执行顺序；同一链路的用例可串行成组，保证单条也能跑。
6. **幂等与并发**：重复提交类用例显式生成独立幂等键；并发用例用线程或连接池并发发起并断言最终只落一条；断言前先确认写入完成（轮询接口或查库），不用固定等待。
7. **数据与清理**：唯一值（手机号、设备号、编码）用生成规则构造，不复用固定值；写操作必须可回收——用造数接口删、或按业务标记字段恢复逻辑删除，只删本用例期间新增的差集，不按 id 区间批量删；环境数据被消耗完时跳过用例。
8. **超时与重试**：超时取配置，重试只用于幂等只读请求，且重试次数上限写死；禁止 `sleep` 与固定延时，异步结果用轮询。
9. **标注与报告**：按仓库既有报告工具分类——模块级 feature、功能分组的 story、带用例编号前缀的 title、由优先级换算的 severity；打齐冒烟/回归/慢速/安全/破坏性标记，新标记同步注册。关键步骤包成步骤块。
10. **自检**：每条脚本能追溯到原用例编号；每例有断言且分传输层与业务层；全文无 `sleep`、无编造路径字段、无硬编码凭据与 token；写操作都有清理；能跑一遍，或说明为何未跑（缺环境、缺账号、缺契约）。

## 分栈落地参考

只有定了栈才看对应一行；表里没有的栈按该栈官方骨架写，只保留上面的通用原则。

| 场景 | 典型骨架 | 该栈的落地点 |
| :--- | :--- | :--- |
| 接口·Pytest + requests | `api/<module>/`、`data/`、`tests/`、`conftest.py` | Client 封装请求与解析，鉴权、超时、重试在 fixture；断言用状态码 + 业务码 + 字段 |
| 接口·Postman + Newman | Collection + 环境变量 + `newman run` | 用例映射到 request 项，前置与断言写在 Tests 脚本；环境与 token 走 environment |
| 接口·Jest + supertest | `tests/`、`api/`、`fixtures/` | 直接对 app 发请求，断言链式表达；数据准备与清理放 beforeAll/afterAll |
| 接口·Karate / RestAssured（Java） | `src/test/resources/` 或 `src/test/java/` | 用 feature 文件或断言链；契约校验走 schema 匹配 |
| 接口·GraphQL / gRPC / 消息队列 | `api/<module>/`、`schema/` 或 `proto/`、`cases/` | 断言改为 schema 或契约校验 + 业务错误码，不假设有 HTTP `code`；序列化与鉴权放 Client |
| 契约测试（Pact 等） | `contracts/`、`pacts/` | 只验消费方与提供方的契约一致，不重复验业务行为 |

## 输出格式

产物为单个 Markdown 文档，可直接另存为 `.md` 交付或入库。

- 文首写一级标题（产物名），下一行写 `> 来源：<上游产物或用户材料>｜生成：YYYY-MM-DD`
- 节标题统一用中文序号加固定名（一、xxx、二、xxx），名称不改，供下游按标题定位；模块级标题写「模块：<模块名>」
- 列表与表格用原生 Markdown，不用代码围栏包裹；代码围栏只包裹真正的代码
- 表格列序与列名、编号格式固定，不按现状重排
- 不输出 HTML、图片、Excel、CSV 或散装纯文本


### 一、设计简述

选了哪套栈与依据、目录与分层、鉴权与数据策略、依赖顺序处理、清理策略。

### 二、用例映射表

`原用例编号 → 文件 → 函数或请求项 → 状态（可运行 / skip 待补）`。

### 三、代码

按文件分块（Client → 数据或 fixture → 用例），只给新增与改动部分；注释写业务意图与易踩点（如「该接口返回业务码 0 才是成功，HTTP 恒为 200」），不解释语法。

### 四、运行说明

依赖安装、环境变量与账号配置、执行命令（全量 / 单模块 / 单用例 / 按标记）、报告命令、失败产物位置、重跑方式。

### 五、待补清单

缺的接口路径与字段、契约文件、测试账号、需要 mock 的外部依赖，逐条说明需要谁提供什么。

## 禁止

- 不编造 path、入参字段、返回字段、业务码；缺就占位并标记跳过。
- 不用 `sleep` 与固定延时；异步结果用轮询，重试只用于幂等只读请求。
- 不把 HTTP 200 当作业务成功；不省略业务码断言。
- 不对整个响应体做全等比较，只断言关键字段与契约结构。
- 不在 Client 里写断言与业务判断；不在用例层重复拼装请求细节。
- 不硬编码凭据与 token，不把它们打印到日志。
- 写操作不做清理；用 id 区间批量删数据。
- 不改写用例的业务预期以让脚本通过；预期与实现冲突时保留原预期并报告。
