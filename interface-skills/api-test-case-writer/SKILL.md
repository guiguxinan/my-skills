# 接口测试用例编写

产出的每条用例，必须是另一个测试人员不看需求也能照着发请求、判断成败的序列。

## 输入

- 上游（优先）：`api-test-point-generator` 的「测试点清单」，按 TP 编号对齐，一个测试点可展开为多条用例。
- 单独调用：接口文档、抓包样例、测试点、已有用例表（Excel、CSV、Markdown 均可；先解析列结构再映射，不默认列名）。
- 必填上下文：接口地址与鉴权方式、测试账号与角色、依赖数据（前置记录、唯一键）。缺失时列进「数据准备清单」并标 `[待准备]`，不虚构 ID 或报文。
- 已有用例表作为输入时：保留原文编号，只补缺与修正，不重排既有编号。

## 执行

1. **分组与编号**：按模块 → 链路 → 用例三级组织。编号 `TC-<模块缩写>-<三位序号>`，组内连续、不复用；沿用用户既有编号体系则照其续号。
2. **写前置条件**：只写「发请求前必须已成立的状态」——鉴权已就绪（token 如何获取）、依赖数据已存在（哪条记录、什么状态）、服务可访问、幂等键已生成。前置里出现「调用某接口」属于步骤，不要写成前置。
3. **写请求步骤**：一步一个请求，写清 method + path + 关键入参（逐字段给具体值或占位符），需要取上游返回值时写明取哪个字段（如 `orderId ← 上一步 data.orderId`）。不在一步里串多个请求，不写「调用相关接口」这种含糊表述。
4. **写预期结果**：与步骤同序号一一对应，写清传输层与业务层两件事——HTTP 状态码、业务码（两者分开写，不当成同一件事）、关键字段值或类型、副作用（落库记录、状态变更、消息发出、缓存更新），以及不该发生的事（不落库、不重复生成）。不写「返回成功」「无异常」。
5. **配数据**：步骤里给出具体取值并注明来源（固定测试账号 / 新建 / 造数接口）。每个入参字段都要有独立边界用例（必填、类型、长度上限与上限+1、枚举、特殊字符），不能一条「必填校验」代表整个接口。需要唯一值（手机号、设备号、编码）时给出生成规则，不用固定值反复跑。
6. **定优先级**：P1 主链路正向、资金与数据一致性、鉴权绕过，P2 一般参数与状态异常，P3 边界组合与低频容错。团队用 P0–P2 时按 P1→P0、P2→P1、P3→P2 映射并在文首注明。
7. **自检**：步骤数与请求数一致；每条预期同时含传输层与业务层结论；前置不含调用动作；每个入参字段都有独立边界用例；编号连续无跳号；引用数据的用例都能在数据准备清单里找到条目。

## 输出格式

产物为单个 Markdown 文档，可直接另存为 `.md` 交付或入库。

- 文首写一级标题（产物名），下一行写 `> 来源：<上游产物或用户材料>｜生成：YYYY-MM-DD`
- 节标题统一用中文序号加固定名（一、xxx、二、xxx），名称不改，供下游按标题定位；模块级标题写「模块：<模块名>」
- 列表与表格用原生 Markdown，不用代码围栏包裹；代码围栏只包裹真正的代码
- 表格列序与列名、编号格式固定，不按现状重排
- 不输出 HTML、图片、Excel、CSV 或散装纯文本

按模块分组，一个模块一节一张表，标题写 `#### 模块：<模块名>（链路 <链路ID>）`。列序固定不调换：优先级紧跟用例标题；表头名称固定，便于下游 `api-automation-feasibility-analyzer` 按列名解析。下方 4 条为结构示例。

#### 模块：订单（链路 CL-01）

| 用例编号 | 关联测试点 | 用例标题 | 优先级 | 前置条件 | 请求步骤 | 预期结果 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| TC-ORDER-001 | TP-ORDER-001 | 正常创建订单 | P1 | 买家账号 token 有效；购物车存在 1 件可售商品；库存充足 | 1. POST /api/order/create，body 含 `items=[{skuId, qty:1}]`、`requestId=<uuid>` | 1. HTTP 200，业务码 0，`data.orderId` 非空且为字符串；库中新增 1 条待支付订单，库存扣减 1 |
| TC-ORDER-002 | TP-ORDER-002 | 缺少 items 字段提交 | P2 | token 有效；其余字段正常 | 1. POST /api/order/create，body 不含 `items` | 1. HTTP 200 或 400，业务码为「参数缺失」；不生成订单，库存不变 |
| TC-ORDER-003 | TP-ORDER-003 | 收货人姓名长度达上限 | P2 | token 有效；该姓名长度已知为 20 字上限 | 1. POST /api/order/create，body 含 `receiverName`=20 字 | 1. 请求成功，订单 `receiverName` 落库与入参一致 |
| TC-ORDER-004 | TP-ORDER-003 | 收货人姓名超过上限 1 位 | P2 | token 有效 | 1. POST /api/order/create，body 含 `receiverName`=21 字 | 1. 返回业务码「姓名超长」；不生成订单 |

每批用例后附两张表：

### 二、编号规则

`TC-<模块缩写>-<三位序号>`，模块缩写取模块名首字母大写（ORDER、USER、PAY）；模块内连续不跳号；沿用用户既有编号体系时据其续接。

### 三、数据准备清单

| 数据项 | 用途 | 状态 |
| :--- | :--- | :--- |
| 买家账号 token（有效期内） | TC-ORDER-001/002/003/004 | 已有 |
| 可售商品 skuId + 库存 ≥10 | TC-ORDER-001/002 | [待准备] |
| 收货人姓名长度上限实际值 | TC-ORDER-003/004 | [待确认] |
| requestId 生成规则（uuid v4） | 全部写接口用例 | 已有 |

状态只取三种：`已有` / `[待准备]`（数据要造） / `[待确认]`（规则值未定）。`[待确认]` 只登记在本表，用例正文写成「（按实际上限值）」，不编数字。

## 脚本

`scripts/` 下的辅助脚本，用于用例表自检：

| 脚本 | 用途 |
| :--- | :--- |
| `scripts/check_cases.py` | 逐条校验：编号格式与模块内连续性（不跳号、不重号）、请求步骤数与预期条数是否一一对应、前置条件是否混了调用动作、优先级取值是否合法、有没有写死的手机号 / 账号。接口用例的步骤列名是「请求步骤」，用 `--steps-header 请求步骤` 指定；编号与优先级体系不同用 `--id-regex` / `--allow-priority` 适配。 |
| `scripts/mdutil.py` | Markdown 通用读写工具库（表格解析、章节替换、代码块提取、标题统计）。 |

用法示例：

```bash
python scripts/check_cases.py ../../test-design/api/03-测试用例.md --steps-header 请求步骤
```

发现问题时改文档，不要改脚本去迁就文档。

## 禁止

- 不把多个场景或多种边界取值合并成一条用例。
- 不编造接口路径、入参字段、返回字段、业务码；写成「（业务码按实际补充）」并进 `[待确认]`。
- 不把 HTTP 状态码与业务码混为一谈，也不写「返回 200 即成功」这种含混结论。
- 不省略鉴权前置与依赖数据的获取方式；拿不到 token 的用例无法执行。
- 不用固定唯一值（手机号、设备号、编码）反复跑；给生成规则或造数方式。
- 不写界面操作步骤（点击、进入页面），那是 UI 用例的职责。
- 不输出自动化判断、脚本或覆盖统计——分池与编码是下游 Skill 的职责。
