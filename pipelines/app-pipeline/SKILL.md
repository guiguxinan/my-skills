# App 测试设计流水线

参数按空格顺序解析：第 1 个是输入（apk/ipa 路径、小程序体验码、截图或录屏路径、需求材料路径），第 2 个是输出目录（缺省为当前项目的 `test-design/app/`），第 3 个是止步位置（缺省 5）。

## 步骤

一步做完再进下一步，不跳步、不并步、不提前写下一步的产物。

| 步 | Skill | 产物文件 | 输入 |
| :--- | :--- | :--- | :--- |
| 1 | `app-core-link-analyzer` | `01-核心链路清单.md` | 安装包或小程序／截图／需求材料 + 可运行的设备 |
| 2 | `app-test-point-generator` | `02-测试点清单.md` | 01 |
| 3 | `app-test-case-writer` | `03-测试用例.md` | 02 |
| 4 | `app-automation-feasibility-analyzer` | `04-自动化选型.md` | 03 |
| 5 | `app-automation-script-generator` | `05-自动化脚本.md` | 04 |

## 规则

- 每步只按该步的 Skill 规则产出，不把下一步的判断（优先级分池、脚本结论）提前塞进这一步。
- 每个文件是完整 Markdown 文档：`# 标题` + `> 来源：<上一步文件>｜生成：<日期>` + 该 Skill 规定的各节；不用代码围栏包裹清单与表格。
- 上一步的「假设与待确认」原样带进下一步并累计，不删、不合并、不改写。
- 某步缺材料（无设备、装不上包、要登录但没账号、车辆未绑定、无控件标识）时：在该步停下，只问能改变结论的问题（不超过 3 个），拿到答复再继续；不许用假设硬推进到下一步。
- 设备、系统版本、App 版本在第 1 步就登记清楚，后续每步沿用同一套编号，不中途换设备说法。
- 止步位置给了就跑到第 N 步为止，交付 1–N 的文件，并写清后面几步各需要什么输入。
- 全部结束后输出一张汇总表：步 / 文件路径 / 节数 / 未决待确认项数 / 建议下一步。
