# App 自动化适用性分析

端上自动化的成本大头是设备与控件识别，不是脚本本身；分池要按这个成本算。

## 输入

- 上游（优先）：`app-test-case-writer` 的用例表，按用例编号对齐。
- 单独调用：任意来源的用例表（Excel/CSV/Markdown）、用例列表、场景清单。
- 先解析列结构：识别 编号/标题/优先级/前置/步骤/预期（外部表格列序可能不同，按列名映射而非按位置猜）。缺步骤列时只能按标题与预期推断可断言性，结论标 `[信息不足]` 并降低置信度。
- 额外增益输入（有则用）：控件是否带 accessibility id 或 testID、控件树是否稳定、有无测试账号与测试车辆（或可造数接口）、有无多机型设备池、CI 是否支持真机。

## 执行

1. **五维打分**，每维 1–5，写分值不写形容词：

   | 维度 | 5 分情形 | 1 分情形 |
   | :--- | :--- | :--- |
   | 执行频次 | 每次发版必回归 | 一次性活动验证 |
   | 控件稳定性 | 控件带稳定标识、界面与交互半年未变 | 全靠文案或坐标定位、页面每周改版 |
   | 数据可构造 | 测试账号、车辆/设备、订单都能造能清 | 依赖真实车辆、真实硬件或生产数据 |
   | 断言可判定 | 有明确页面状态、控件值、文案 | 只能人工看观感、听音效、感受震动 |
   | 单次执行成本 | 手工需跨机型反复验证、单次 10 分钟以上 | 手工点两下即完成 |

2. **按总分定池**：≥18 可自动化；12–17 有条件自动化（需先补控件标识、设备池或造数能力）；<12 手工。
3. **先过一票否决**，命中即入手工池，不论分数多高：需人工感官判断（动画流畅度、动效、音效、震动、拟真度）；依赖真实车辆或硬件动作（蓝牙钥匙、GPS 实际位移、OBD 数据）；依赖系统级不可控事件（来电、厂商 ROM 特有问题、系统权限弹窗无法稳定应答）；加固或反调试导致无法驱动；一次性活动；破坏性且不可回滚的数据操作。
4. **定类型**：界面状态足以自证的判纯 UI；需要接口造数或数据层核对后果的判混合；同一用例要在多机型上跑的判兼容矩阵，并单列机型组合。别把「必须查库才能确认」的用例判成纯 UI。
5. **给改造前置**：把「有条件」转成「可自动化」的最小动作，写成可指派的任务——给关键控件补 accessibility id、申请固定测试账号与测试车辆、加清数据与重置脚本、把定位与蓝牙能力 mock 掉、把前置数据改成接口造数。
6. **排批次**：P1 且高频的先做，作为第一批；第一批控制在 10–20 条以验证框架与设备链路可用，其余按模块成批；兼容矩阵用例单独成批，按设备分片跑。
7. **给收益口径**：按「用例数 × 单次执行时长 × 年回归次数 × 机型数」估算节省工时，写清假设值。

## 输出格式

产物为单个 Markdown 文档，可直接另存为 `.md` 交付或入库。

- 文首写一级标题（产物名），下一行写 `> 来源：<上游产物或用户材料>｜生成：YYYY-MM-DD`
- 节标题统一用中文序号加固定名（一、xxx、二、xxx），名称不改，供下游按标题定位；模块级标题写「模块：<模块名>」
- 列表与表格用原生 Markdown，不用代码围栏包裹；代码围栏只包裹真正的代码
- 表格列序与列名、编号格式固定，不按现状重排
- 不输出 HTML、图片、Excel、CSV 或散装纯文本

## 脚本

`scripts/` 下的辅助脚本，用于打分核算与分池校验：

| 脚本 | 用途 |
| :--- | :--- |
| `scripts/score_cases.py` | 五维打分与分池核算。`--template` 生成打分 CSV 模板（按上游用例编号预填），填完用 `--csv` 算汇总表草稿；对本步产物用 `--verify` 核对「可自动化 / 有条件 / 手工」三张表与「三、汇总」的数字是否自洽、分池区间有无越界。 |
| `scripts/mdutil.py` | Markdown 通用读写工具库（表格解析、章节替换、代码块提取、标题统计）。 |

用法示例：

```bash
python scripts/score_cases.py ../../test-design/app/03-测试用例.md --template scores.csv
python scripts/score_cases.py ../../test-design/app/04-自动化选型.md --verify
```

## 禁止

- 不给逐条打分的空转结论：每条必须有总分、判定依据、可执行的下一步。
- 不以「Appium 能点到」作为可自动化理由；能点到说明可行，不等于值得做。
- 不跳过一票否决直接看分数。
- 不把「兼容性差异」整体判成可自动化，也不整体判成手工；要落到具体机型组合。
- 不把用例改写成新用例，也不生成脚本——编码是 `app-automation-script-generator` 的职责。
- 不虚构执行频次、控件稳定性等输入中不存在的事实，缺失时标 `[待确认]` 并在汇总里注明假设。
