# App 测试用例编写

产出的每条用例，必须是另一个测试人员拿着同一台设备、不看需求也能照做的操作序列。

## 输入

- 上游（优先）：`app-test-point-generator` 的「测试点清单」，按 TP 编号对齐，一个测试点可展开为多条用例。
- 单独调用：测试点、页面描述、截图、已有用例表（Excel、CSV、Markdown 均可；先解析列结构再映射，不默认列名）。
- 必填上下文：App 版本号、设备（型号与系统版本）、登录账号、权限与绑定状态（车辆或设备）。缺失时列进「数据准备清单」并标 `[待准备]`，不虚构账号与 VIN。
- 已有用例表作为输入时：保留原文编号，只补缺与修正，不重排既有编号。

## 执行

1. **分组与编号**：按模块 → 链路 → 用例三级组织。编号 `TC-<模块缩写>-<三位序号>`，组内连续、不复用；沿用用户既有编号体系则照其续号。
2. **写前置条件**：只写「执行前必须已成立的状态」——已安装指定版本、设备按环境矩阵编号（如 `设备 E1`）、账号状态、权限已授予或已拒绝、车辆已绑定且在线、网络状态。前置里出现操作动作即写成步骤了，移回步骤。
3. **写步骤**：一步一个动作，动词开头，按真实触碰路径排序（打开 → 进入某屏 → 点击或长按或滑动 → 输入 → 观察）。不合并多动作成一步，不写「验证 X」当步骤。端上动作要写具体手法：点按、长按、右滑返回、下拉刷新、切到后台；涉及系统弹窗时写清在哪个系统弹窗上点什么。
4. **写预期结果**：与步骤同序号一一对应，只写界面可判定的事实——哪一屏、弹层或 Toast 出现、按钮可用或置灰、文案原文、列表条数、开关状态、页面标题。不写「是否发出请求」「是否落库」「接口返回什么」这类跨层断言。不写「正常显示」「成功」「无误」。
5. **配数据**：步骤里直接写出具体取值并注明来源（已有账号 / 新注册 / 接口造数 / 后台配置）。每个输入项都要有独立边界用例（空、上限、上限+1、特殊字符），一条只验一个边界。涉及车辆、设备、订单的取值给出构造方式，不用固定值反复跑。
6. **定优先级**：P1 主链路正向、资金与数据一致性、授权链阻断；P2 一般异常与边界；P3 兼容矩阵与低频交互。团队用 P0–P2 时按 P1→P0、P2→P1、P3→P2 映射并在文首注明。
7. **自检**：步骤数与动作数一致；每条预期可判定真假且不跨层；前置无操作动作；每个输入项都有独立边界用例；设备与版本能在环境矩阵里找到；编号连续无跳号。

## 输出格式

产物为单个 Markdown 文档，可直接另存为 `.md` 交付或入库。

- 文首写一级标题（产物名），下一行写 `> 来源：<上游产物或用户材料>｜生成：YYYY-MM-DD`
- 节标题统一用中文序号加固定名（一、xxx、二、xxx），名称不改，供下游按标题定位；模块级标题写「模块：<模块名>」
- 列表与表格用原生 Markdown，不用代码围栏包裹；代码围栏只包裹真正的代码
- 表格列序与列名、编号格式固定，不按现状重排
- 不输出 HTML、图片、Excel、CSV 或散装纯文本

按模块分组，一个模块一节一张表，标题写「模块：<模块名>（链路 <链路ID>）」。列序固定不调换：优先级紧跟用例标题；表头名称固定，便于下游 `app-automation-feasibility-analyzer` 按列名解析。下方 4 条为结构示例，真实产出按同一列序展开到该模块的全部用例。

### 二、编号规则

`TC-<模块缩写>-<三位序号>`，模块缩写取模块名首字母大写（CTRL、USER、ORDER）；模块内连续不跳号；沿用用户既有编号体系时据其续接。

### 三、数据准备清单

| 数据项 | 用途 | 状态 |
| :--- | :--- | :--- |
| 账号 test01 / 已登录态 | 全部用例 | 已有 |
| 已绑定且在线车辆（VIN: 待填） | TC-CTRL-001/002/003/004 | [待准备] |
| 备注长度上限实际值 | TC-CTRL-003/004 | [待确认] |
| 短信验证码获取方式 | 需要重新登录时 | [待确认] |

状态只取三种：`已有` / `[待准备]`（数据要造） / `[待确认]`（规则值未定）。`[待确认]` 只登记在本表，用例正文写成「（按实际上限值）」，不编数字。

### 四、环境矩阵

| 设备编号 | 型号 | 系统版本 | 分辨率 | 网络 | 备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| E1 | （主力机型） | Android 13 | 1080×2400 | Wi-Fi | 主执行设备 |

## 脚本

`scripts/` 下的辅助脚本，用于用例表自检：

| 脚本 | 用途 |
| :--- | :--- |
| `scripts/check_cases.py` | 逐条校验：编号 `TC-<模块>-<序号>` 格式与模块内连续性、步骤与预期是否一一对应、前置条件是否混了操作动作、优先级取值是否合法、用例引用的设备编号是否在环境矩阵里、有没有写死的手机号 / VIN / 车牌。编号体系与优先级取值随项目不同，用 `--id-regex` / `--allow-priority` 适配。 |
| `scripts/mdutil.py` | Markdown 通用读写工具库（表格解析、章节替换、代码块提取、标题统计）。 |

用法示例：

```bash
python scripts/check_cases.py ../../test-design/app/03-测试用例.md
```

发现问题时改文档，不要改脚本去迁就文档。

## 禁止

- 不把多个场景合并成一条用例，也不用一条用例覆盖多个边界取值。
- 不在 App 用例里写跨层断言（是否发请求、是否落库、接口返回码），这类结论交给接口用例。
- 不编造提示文案、阈值数字、Z 界面文案；写成「（按实际替换）」并登记到 `[待确认]`。
- 不虚构账号、VIN、订单号；缺失一律进数据准备清单标 `[待准备]`。
- 不把「切后台」「杀进程」写成一句「异常操作」；要写明在什么时机、从哪一屏切走。
- 不输出自动化判断、脚本或覆盖统计——分池与编码是下游 Skill 的职责。
- 不重复添加用户编辑过的文档里的编号，也不因重写而打乱既有引用。
