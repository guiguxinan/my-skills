# Web 自动化适用性分析

给出可执行的三分池结论和依据，而不是「这些页面都能点通，都可以自动化」。分池必须**在写脚本之前**产出：它决定后面要写多少脚本、先写哪批、哪些条目要花钱改环境。

## 输入

- 上游（优先）：`web-test-case-writer` 的用例表，按用例编号对齐。
- 单独调用：任意来源的用例表（Excel/CSV/Markdown/JSON）、用例列表、页面场景清单。
- 先解析列结构：识别 编号/标题/优先级/前置/步骤/预期（外部表格列序可能不同，按列名映射而非按位置猜）。缺步骤列时只能按标题与预期推断可断言性，结论标 `[信息不足]` 并降低置信度。
- 额外增益输入（有则用）：是否存在稳定的自动化定位标识（testid、accessibility id、控件路径、业务主键）；是否存在可用的造数接口；页面是否频繁改版；CI 环境与数据库是否可访问；是否有固定的多角色测试账号。

## 执行

0. **先归一化**：表格来源先用 `scripts/case_table_reader.py` 读成标准 JSON（列名不匹配时用 `--map` 补映射），再跑 `scripts/signal_scan.py` 得到候选判据与卡点分布。信号只是候选，命中词可能只是文案巧合，逐条仍需人判。
1. **五维打分**，每维 1–5，写分值不写形容词：

   | 维度 | 5 分情形 | 1 分情形 |
   | :--- | :--- | :--- |
   | 执行频次 | 每次发版必回归 | 一次性活动验证 |
   | 稳定性 | 界面结构与交互半年未变 | 页面每周改版 |
   | 数据可构造 | 接口一键造数与清数 | 依赖生产真实数据、只能手工摆数据 |
   | 断言可判定 | 有明确状态、字段、文案、文件内容 | 只能人工看观感 |
   | 单次执行成本 | 手工需 10 分钟以上 | 手工点两下即完成 |

2. **先过一票否决**，命中即入手工池，不论分数多高：依赖人工视觉/听觉/主观判断（配色、动效、语气、拟真度、版式观感）；一次性活动或时效性验证；破坏性且不可回滚的数据操作；强依赖真实第三方与人工审批；极端难构造的异常（特定并发窗口、硬件故障）。
3. **按总分定池**：≥18 可自动化；12–17 有条件自动化（需先补定位标识、测试数据、断言手段或造数接口）；<12 手工。三条池必须分开成节，不许把「有条件」混进「可自动化」。
4. **定类型**：只有在界面上才看得见、且页面状态足以证明的判纯 UI（展示、交互态、权限可见性、多端一致性）；操作走界面而断言落在接口、数据库或文件产物的判混合。别把「必须查库才能确认」的用例判成纯 UI。
5. **给改造前置并落到脚本**：把「有条件」转成「可自动化」的最小动作，写成可指派的任务，同时按下方「前置类型 → 脚本」表给出**具体脚本名与关键参数**。只写「要补脚本」不算结论。
6. **排批次**：P1 且高频的先做，作为第一批；第一批控制在 10–20 条以便快速验证框架可用，其余按模块成批。条件未补齐的条目排在对应前置完成之后。
7. **给收益口径**：按「用例数 × 单次执行时长 × 年回归次数」估算节省工时，写清假设值，不写「大幅提升效率」。

## 前置类型 → 脚本

卡点不是形容词，是「缺哪一双手」。按下表判定卡点类型，并在有条件清单的「可用脚本」列写出脚本与参数。

| 卡点类型 | 表现 | 用哪个脚本 | 关键参数 |
| :--- | :--- | :--- | :--- |
| P1 定位标识缺失 | 只能按坐标或文案定位，改版即失效 | 无（转开发补 data-testid 或用业务主键定位） | — |
| P2 账号与权限 | 依赖非管理员、多角色、越权场景 | `checks.py api` | `--cookie` / `--headers-file` 换不同账号 token 比对响应 |
| P3 造数与清数 | 没有造数接口，数据只能手工摆 | `fixture_guard.py snapshot` + `checks.py db` | `--query-file` 定义基线查询，`--key` 指定主键 |
| P4 破坏性写操作 | 删除、覆盖、直接写库，无法回滚 | `fixture_guard.py snapshot / diff / plan-restore` | `--key-column` 指定主键；回滚 SQL 只生成不执行 |
| P5 文件产物断言 | 导出件、模板、失败明细要人眼逐格看 | `checks.py artifact` | `--rule-file` 支持 cell / header / row / rowcount / merged |
| P6 库断言 | 页面没有可判定信号，结论只在库里 | `checks.py db` | `--dsn`、`--query-file`、`--expect-rows` / `--expect-value` |
| P7 绕过前端 | 前端截断、maxlength、二次校验挡在前面 | `checks.py api` | `--body-file` 直接构造请求体，`--expect-json` 断言服务端返回 |
| P8 并发与幂等 | 连点、重复提交、短时间窗 | `checks.py api --repeat` | `--repeat N` + `--expect-one-success` 断言只成功一次 |
| P9 外部依赖 | 短信、支付回调、人工审批 | 无（需 mock 或沙箱服务） | — |
| P10 视觉基线 | 配色、版式、图片比例、地图落点观感 | 无（另配截图基线对比与像素阈值） | — |

无脚本可解的 P1 / P9 / P10 类，直接写「不投入自动化，保留手工并注明豁免原因」，不要为了凑数编一个脚本。

## 输出格式

产物为单个 Markdown 文档，可直接另存为 `.md` 交付或入库。

- 文首写一级标题（产物名），下一行写 `> 来源：<上游产物或用户材料>｜生成：YYYY-MM-DD`
- 节标题统一用中文序号加固定名（一、xxx、二、xxx），名称不改，供下游按标题定位；模块级标题写「模块：<模块名>」
- 列表与表格用原生 Markdown，不用代码围栏包裹；代码围栏只包裹真正的代码
- 表格列序与列名、编号格式固定，不按现状重排
- 不输出 HTML、图片、Excel、CSV 或散装纯文本
- 直接调用 `scripts/pool_report.py` 可按本节结构生成骨架，再补写判定依据

## 脚本

本 skill 自带 `scripts/`（用法见 `scripts/README.md`），全部不绑定项目，换项目只改传入的表名、URL、连接串与规则文件：

```bash
python scripts/case_table_reader.py --input 用例表.xlsx --out cases.json
python scripts/signal_scan.py --input cases.json --out signals.json
python scripts/pool_report.py --input assessment.json --out 分池.md
python scripts/checks.py artifact --file 导出.xlsx --rule-file rules.json
python scripts/checks.py api --method POST --url "$BASE/xxx/add" --body-file body.json --expect-json '{"code":500}'
python scripts/checks.py db --dsn "mysql://u:p@h/db" --query-file queries.json
python scripts/fixture_guard.py snapshot --dsn "mysql://u:p@h/db" --query-file q.json --out before.json
```

依赖缺失时脚本会明确报出要装什么（`openpyxl` 读表、`pymysql`/`psycopg2` 连库、`playwright` 做 dom 断言）；不要假设它们已安装，也不要静默跳过该条用例。

另有跨档位通用的两个脚本：

| 脚本 | 用途 |
| :--- | :--- |
| `scripts/score_cases.py` | 五维打分与分池核算。`--template` 生成打分 CSV 模板（按上游用例编号预填），填完用 `--csv` 算汇总表草稿；对本步产物用 `--verify` 核对「可自动化 / 有条件 / 手工」三张表与汇总表的数字是否自洽、分池区间有无越界。 |
| `scripts/mdutil.py` | Markdown 通用读写工具库（表格解析、章节替换、代码块提取、标题统计）。 |

```bash
python scripts/score_cases.py ../../test-design/web/03-测试用例.md --template scores.csv
python scripts/score_cases.py ../../test-design/web/04-自动化选型.md --verify
```

## 禁止

- 不给逐条打分的空转结论：每条必须有总分、判定依据、可执行的下一步。
- 不把「有条件自动化」混进可自动化清单凑数；三条池必须分别成节，条数之和等于输入总数（扣除 `[信息不足]` 并单列）。
- 不以「UI 能点通」作为可自动化理由；能点通说明可行，不等于值得做。
- 不跳过一票否决直接看分数。
- 不写「需补脚本」「需造数」这类没有脚本名与参数的改造前置；也不声称某个脚本可用却没确认依赖是否就位。
- 不把用例改写成新用例，也不生成正式测试脚本——编码是 `web-automation-script-generator` 的职责；本 skill 只交付分池结论与前置工具。
- 不虚构执行频次、改版频率等输入中不存在的事实，缺失时标 `[待确认]` 并在汇总里注明假设。
